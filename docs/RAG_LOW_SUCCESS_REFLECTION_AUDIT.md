# RAG 低成功率反思审计（v0.1）

> 目的：回答“为什么已经做了多轮数据、失败分析和候选迭代，RAG 的路由、证据关系和召回仍然很低”，并决定下一步应该修哪里。本文是一次反思审计，不是新的质量评测，不会把候选升为现役。
>
> 本轮审计范围：只读取公开评测、V4 answerless 盲测聚合、V4 answerless Trace、公开失败驱动 Loop 和生命周期摘要；不读取新的隐藏答案、不读取 V4 解冻题目/Gold、不读照片/向量、不调用网络/LLM/Provider。

## 1. 先给结论

这几轮优化没有真正把 RAG 优化到应有水平，最主要的原因不是“流程没有坚持下来”，而是**每轮实际测到的对象不一致**：大多数 V4 题目在“自然语言变成结构化检索请求”之前就结束了，根本没有进入检索；评测器还把上游投影出来的路由和证据别名混进了最终答案。因此当前低分主要暴露的是“听懂问题、拆出任务和安全约束”的入口问题，而不能直接归因于 P0-B 的向量召回或重排序。

同时，知识库目前只有 3 张审核过的 Provider Card、10 条有效规则，无法独立支撑题目要求的隐私、生命周期、冲突和提示注入判断；盲测还使用了可重复的离线词元测试后端，不是线上真正的语义模型链路。最后，固定 `Precision@3=0.80` 在当前 Gold 条数分布下数学上不可达，进一步把“评测口径问题”和“产品能力问题”混在了一起。

所以，继续增加题目、继续调 Top-K、继续在最后输出上补丁，都不能可靠解决问题。下一步应先拆开评测合同，让系统真正经过“自然语言 → 结构化查询 → 召回 → 证据采用 → 路由”这条链路，再判断检索算法是否需要优化。

## 2. 我是怎么反思的

本轮把问题拆成六个问题来查，而不是只看一个总分：

1. 每一轮到底改了哪个层，真的改变了输入/检索，还是只改了最后的标签？
2. V4 低分的题目有没有真正进入 RAG 检索？
3. 评测结果中的“证据”是否来自知识库，还是来自评测器提前写入的投影？
4. 知识库是否真的有题目要求的资料？索引同步是否被误认为知识完整？
5. 指标的分母、Gold 稀疏、多路由和关系评分是否合理？
6. 离线盲测和线上 DeepSeek→IntentFrame→RagQuery 是否在测同一个东西？

独立审计者在不读取受限逐题答案的前提下复核了公开代码、V4 聚合和 answerless Trace，结论与本报告一致：**先修测量边界和上游编译边界，不要先调排序模型。**

## 3. 迭代时间线：流程没有错，但修复层次一度错了

| 阶段 | 实际做了什么 | 结果 | 现在如何理解 |
|---|---|---|---|
| 早期公开集 V0→V2 | 对已经生成的 Prediction 做同义词、关系名称和证据整理 | Composite=`0.947436`，每代改变 `0` 条事实 | 优化没有触达失败发生的入口；公开集本身也过于容易 |
| 失败驱动开发集 V0 | 以窄短语投影作为基线 | Composite=`0.355614`，Route=`14.29%`，Relation=`28.57%`，Recall@5=`50.00%` | 第一次把失败放到更靠前的自然语言入口 |
| 失败驱动开发集 V1 | 加入审核过的同义词归一化 | Composite=`0.403233`，改变 `2` 条预测 | 有真实改善，但仍只是开发/挑战集证据 |
| 失败驱动开发集 V2 | 加入任务信号、动作/信息优先级、安全/生命周期优先级和多意图证据编译 | Composite=`0.947619`，改变 `22` 条预测；开发集语义指标达到 100% | 说明“修到上游”方向是对的，但没有证明泛化 |
| 失败驱动开发集 V3/V4 | 继续做关系守门、证据打包等下游整理 | 每代改变 `0` 条预测，按边际效益规则停止 | 继续在下游打补丁没有价值 |
| V4 独立盲测 | 48 道新题，只给系统题目，不给答案 | Route=`12.50%`、Relation=`18.75%`、Recall@5=`57.99%`，安全硬门 PASS，质量 Gate FAIL | 真正的新表达仍没有被稳定理解和路由 |

### 3.1 为什么说流程本身不是唯一问题

你设定的“冻结 → 找失败 → 只改一个变量 → 公开回归 → 独立 Holdout → 决定推广”的流程是合理的。真正的问题是：

- 早期候选只改了已经生成的结果，没有改变用户问题如何进入检索；
- V3/V4 解冻后，候选可以看到题目和答案，因此验证集 100% 只是“看过题后的练习成绩”；
- V4 的评分把上游任务理解、真实检索、证据关系和最终路由放在同一个结果里，没有告诉我们究竟哪一层失败；
- “训练集”这个说法不准确：这里没有训练一个模型，主要做的是人工审核的规则工程和离线评测。

因此不是“多跑几轮就会变好”，而是需要先保证每一轮都在同一层、同一条真实链路上测量。

## 4. 最关键的证据：V4 大多数题没有真正检索

### 4.1 V4 盲测看到了什么

| 检查项 | 实际结果 | 直白解释 |
|---|---:|---|
| V4 题目 | 48 | 这是一次新的独立盲测输入 |
| 生成结构化检索请求 | 8 | 只有 8 题被整理成 P0-B 能理解的格式 |
| 没有生成结构化请求 | 40 | 40 题在进入检索前就返回了未知/保守结果 |
| 留下检索 Trace | 8 | 只有 8 题能检查 FTS、dense、RRF、rerank 的过程 |
| `no_reliable_structured_projection` | 36 | 最早失败大多是“没听懂并拆出任务” |

这意味着 V4 的 `Route=12.50%` 不能直接翻译成“向量库只找对了 12.5%”。更准确的说法是：**当前离线桥接器只有少量题目真正走到了检索；大多数题先在自然语言理解/任务投影层失败。**

### 4.2 实际链路与被测链路

产品希望测量的链路是：

```text
用户原话
→ 理解用户在问什么/要做什么
→ 生成结构化检索请求
→ 从审核知识中召回候选
→ 排序和整理证据
→ 区分直接依据、参考信息、冲突信息
→ 提出受限路由建议
→ 状态机、权限策略和 Adapter 决定是否执行
```

V4 baseline 实际更接近：

```text
V4 原话
→ 一个较窄的 phrase projector 尝试匹配
→ 匹配失败就 UNKNOWN + P
→ 只有少数匹配成功的题才进入 P0-B
→ 最终 Prediction 又合并 projection 的路由/别名
```

所以目前存在两个错位：

1. **入口错位**：线上是 DeepSeek IntentFrame Adapter → `build_plan_advisory_query`；V4 离线 runner 为了不调用 LLM，使用独立的 phrase projector。V4 分数不能当作线上 IntentFrame 成功率。
2. **证据错位**：baseline 的 Prediction 先采用 projection 的 route/evidence aliases，再追加真实检索结果；`P`/`FX` 等标签并不是当前知识库中可召回的知识块。这样评分会把“规则投影正确”看成“RAG 检索正确”。

这也是为什么即使 G2 在已解冻验证副本上出现 100%，也不能说 RAG 产品化：它主要证明候选能复现这批已见过的任务分类，不证明在新问题上真实找到并采用了正确知识。

## 5. 知识库不是坏了，而是覆盖远远不够

生命周期审计的当前事实是：

- 审核知识卡：`3` 张；
- 当前有效原子规则：`10` 条；
- 生命周期问题：`0`；
- 派生索引：`in_sync`；
- 主要来源：Tencent BeautifyPic、CompareFace、ImageModeration。

`in_sync` 只说明“索引里的 10 条和当前有效的 10 条数量一致”，不说明“这 10 条已经覆盖题目需要的所有知识”。当前题目还要求系统回答：

- 隐私和图片出站边界；
- 主体锚点同意、到期、撤回和删除；
- 资料过期、冲突、尚未生效；
- 提示注入和未知 Provider；
- 多脸、批量和人工复核；
- 用户反馈与验证策略。

如果这些规则没有以审核过的 Policy/Rule Card 进入知识库，那么 RAG 找不到它们是正常结果。此时由编译器直接返回 `P/FX` 可以作为安全产品规则，但不能计作“召回了一条知识”。

## 6. 这次低分中，排序模型不是第一嫌疑

Gold baseline 为了保证离线完全可重复，明确使用：

- `DeterministicTokenEmbeddingBackend`：按词元做固定哈希，不理解词义；
- `TokenOverlapReranker`：按词语重合程度排序。

这两个后端适合做 fixture 测试，不代表真正 BGE 语义模型的能力。但它们不是当前第一根因，因为 48 道题中有 40 道根本没有生成结构化查询，也就没有进入 dense/RRF/rerank。现在直接更换 embedding 或 reranker，最多改善那 8 道已经进入检索的题，解决不了前面的 40 道。

线上 P0-B 支持本地缓存的 BGE 路径；是否能在当前环境真正加载模型，应该作为拆分评测后的单独实验来验证，不能用 fixture 盲测结果代替。

## 7. 指标为什么让问题看起来更糟

### 7.1 固定 Precision@3 的理论上限

V4 有 23 道题只有 1 条 Gold 证据、24 道题有 2 条、1 道题有 3 条。固定 Precision@3 永远除以 3，因此即使每一题返回的证据全部正确，理论最高值也只有：

```text
(23×1/3 + 24×2/3 + 1×1) / 48 = 0.513889
```

公开集的同一上限约为 `0.474359`。但是冻结项目门槛要求 Precision@3 ≥ `0.80`，所以这个门槛在当前 Gold 结构下不可能通过。

这不是把低 Route 或低 Relation 解释成“统计问题”。Route=`12.50%`、Relation=`18.75%` 仍然是真实质量问题；只是固定 Precision 不能继续作为这一批稀疏 Gold 的有效优化方向。当前应继续并列展示 fixed/effective/returned 三种口径，任何改门槛的动作都要另走产品决策门。

### 7.2 评测器还存在几个需要修复的契约问题

代码审计显示：

- Route 允许把 `BLOCK/BASELINE`、`DIRECT+REFERENCE` 拆成多个 alternatives，命中其中之一就算路由正确；这会把本来需要分步骤处理的任务压扁成一个标签。
- Evidence relation 只检查 Gold 中出现的键是否匹配，没有对额外关系键做同等惩罚；多返回一条关系不一定被扣分。
- nDCG 当前按“是否在 Gold 中”二元计算，尚未真正表达 direct > reference > conflict 的等级差异；文档中的“graded”与代码实现不完全一致。
- Gold evidence aliases 同时包含工具能力和政策标签，导致“检索结果”和“策略结果”混为一组。

这些问题不会让真实失败消失，但会让错误归因和迭代方向不稳定，必须在新的评测合同中拆开。

## 8. 根因排序：事实、解释和预期收益

| 排名 | 根因 | 证据 | 置信度 | 如果修复，先改善什么 |
|---:|---|---|---|---|
| 1 | 自然语言到结构化查询/路由的入口失败 | 40/48 题无结构化查询；36/48 标为 `no_reliable_structured_projection` | 高 | Route、结构化查询覆盖率；随后才可能改善 Recall |
| 2 | 评测器把 projection 事实当作 RAG 证据 | `Prediction` 先合并 projection aliases/route，再加检索结果；P/FX 不在三张 Card 中 | 高 | 证据来源真实性、检索层指标可解释性 |
| 3 | 知识库覆盖不完整 | 3 卡/10 规则，政策与生命周期事实未全部入库 | 高 | Evidence exact/relation；减少“知识库没有资料”和“检索空召回”混淆 |
| 4 | 离线盲测使用 fixture 检索后端 | baseline 明确使用 token hash/overlap 后端 | 高 | 只有在真正检索轨道中才可能改善语义 Recall/排序 |
| 5 | fixed Precision@3 门槛不可达 | V4 理论上限 0.513889 < 0.80 | 高 | 评测解释和产品决策，不会直接提高真实能力 |
| 6 | 解冻验证候选存在验证泄漏/过拟合风险 | G2 在看过答案的 validation 上 100%，原始 V4 blind 仍低 | 高 | 新 Holdout 的可信度；不能靠继续改 V4 得到泛化 |
| 7 | 回归守门仍以逐题结果为主，缺少核心指标 floor | 候选可在部分 case 回退，但 aggregate 语义损失没有独立硬门 | 中 | 防止候选改善一组题却悄悄伤害已知能力 |

## 9. 为什么之前“修复”看起来没有长期效果

这里有两个阶段，不能混成一句“全部无效”：

### 阶段一：确实是无效的后处理

早期 V0/V1/V2 都是 `0.947436`，`changed_prediction_count=0`。因为 public baseline 已经输出了标准化 route/evidence/relation，候选只是把同义词或关系名称改写成同样的标准形式；输入没变、检索没变、实际事实没变，所以分数不动。这是明确的“修错层”。

### 阶段二：上游候选在开发/验证题上有效，但不能证明泛化

失败驱动开发集的 V2 把修正前移到自然语言→查询编译，Composite 从 `0.403233` 到 `0.947619`，说明方向正确；V4 解冻验证的 G2 也能把已见题解释到 100%。但这些数据并不是全新的盲测：开发题用于调规则，解冻验证题已经有答案，候选可以覆盖它们的表达。原始 V4 blind 仍为 Route=`12.50%`、Relation=`18.75%`，说明当前还没有证据证明它能泛化。

所以，**之前的流程有一部分是对的，但实验设计没有把“修复有没有触达真实被测层”和“修复能否泛化”分开。**

## 10. 现在明确不该继续做什么

在评测合同和真实检索边界修好前，暂停以下动作：

1. 不再读取 V3/V4 受限逐题答案继续补词或补 case 规则。
2. 不再把 validation 的 100% 写成 RAG 泛化通过。
3. 不再只调 Top-K、RRF 常数、reranker 或证据数量来抬分。
4. 不用无关证据填固定 Precision@3 的空位。
5. 不把 P/FX 评测标签当成当前知识库已经召回的文档。
6. 不因为安全硬门 PASS 就放宽权限、隐私或图片出站。
7. 不把人工规则编写称作“训练模型”。

## 11. 最小、可验证的下一步（尚不改 active baseline）

### 第一步：建立两条互不混淆的评测轨道

**轨道 A：真实检索轨道。** 输入是已经构造好的 `RagQuery`；Gold 直接使用真实可索引的 chunk ID，并标注 direct/reference/conflict。Prediction 只能来自 retriever/advisory 的 adopted evidence，禁止 projection alias 注入。

**轨道 B：自然语言编译轨道。** 输入是原始用户句子；Gold 是结构化查询槽位、任务路由和安全优先级。它专门评估“听懂用户问题”，不把分数叫作检索 Recall。

### 第二步：做一组 10–15 题的公开 smoke

覆盖同义词、多意图、安全/出站、过期/冲突。逐题查看：

```text
原话（只在内存中）
→ 结构化查询
→ 召回候选数量和来源
→ 采用的证据
→ 最终路由
```

通过标准不是某个总分，而是每题都能证明：如果说“检索到了”，就确实有真实 chunk；如果没有资料，就明确返回“不知道/基线降级”，并留下 bad case 原因。

### 第三步：再决定下一份独立 Holdout 和指标 Gate

等两条轨道和 smoke 都通过后，再由产品负责人决定：

- 是否把隐私/生命周期/冲突整理成 Policy/Rule Card 后纳入检索评测；
- 是否在保留历史 fixed Precision 的同时，新增不受 Gold 稀疏影响的诊断门；
- 是否用真正的本地 BGE 后端跑 canonical retrieval benchmark；
- 是否为候选增加 aggregate no-regression floor；
- 是否建立新的 V5 answerless Holdout。

## 13. 最终产品边界

本轮只完成“理解为什么低、把问题拆到可修的层、给出下一 Gate”；没有更换线上 Agent、没有改变 RAG active baseline、没有改变 Provider/权限、没有把候选提升为现役，也没有建立新的 Holdout。当前准确表述是：

> **完成 V3/V4 失败结果的独立反思审计，确认主要瓶颈在自然语言到结构化查询的上游边界、评测与检索事实混淆、知识覆盖不足和指标口径不可达；下一步先拆分评测合同并验证真实检索链路。RAG 仍为 proposal-only，当前质量 Gate 仍为 FAIL，不能称为已产品化。**

## 15. 负责人确认后的公平评测接续

随后产品负责人确认：两条评测轨道正式采用；隐私、生命周期、过期、冲突和提示注入继续纳入题目；历史 fixed Precision 保留并增加诊断带；当前知识库暂不扩张。为防止答案泄露和漏跑题目，质量评分前新增独立的无答案过程监督考官。
